# Resident Core and UI Client protocol

This document resolves the protocol choice tracked in issue #2 and defines the target contract that issue #4 exercises. The implementation includes real local IPC, protocol negotiation, concurrent controller/observer attachments, a generation-checked Control Lease, commands, pushed terminal invalidations, revision-gated terminal snapshots with lifecycle state, detach, and reconnect.

## Process and transport seam

The Resident Core is a separately restartable, unelevated per-user process. It owns all live domain state, PTY/ConPTY transports, libghostty-vt state, process lifecycle, and agent-integration authority. GPUI runs only in a UI Client process.

`CoreClient` is the concrete UI-facing facade. It exposes semantic commands, revisioned snapshots, subscriptions, and structured errors while keeping application-protocol messages and wire encoding private. It is not a family of remote Space/Tab/Pane objects, and the project will not add a transport trait until a second production transport creates a real abstraction requirement. Its adapter uses a Unix-domain local socket on macOS/Linux and a named pipe on Windows through a cross-platform local-socket implementation. The Resident Core keeps Unix sockets in an owner-verified private runtime directory and restricts peers by effective user ID; the Windows duplex pipe requires creator-authorized write access and derives its otherwise opaque name from the protected per-user secret, preventing another local user from predictably claiming the endpoint first. That 256-bit secret authenticates every server handshake with a fresh HMAC challenge before the client sends any commands. Platform transport types, raw terminal bytes, and libghostty-vt types do not cross the interface.

Protocol version 8 uses one little-endian 32-bit length prefix followed by an
explicit binary payload. Requests, acknowledgements, lifecycle state, and
rendered cell data each have stable field encodings; Rust memory layouts are
never copied onto the wire. A complete frame is assembled before it is written,
which avoids turning each terminal-cell field into a separate socket write.
Frames are rejected before allocation when their declared payload exceeds 16
MiB. The same framed stream may carry coalescible terminal invalidations between
command responses; the client distinguishes them before matching the next
response. Raw PTY bytes remain inside the Resident Core and are consumed
unchanged by libghostty-vt; the binary IPC payload represents commands and
rendered state, not a second terminal byte stream.

## Versioning and attachment

- Every connection begins with a protocol-version and authenticated challenge-response handshake. An incompatible major version or invalid server proof fails closed with a useful error. Connect timeouts cover endpoint discovery and this handshake only; established Unix connections clear that temporary socket timeout before normal commands begin.
- A separate authenticated `recovery-v1` endpoint is stable across application-protocol upgrades and exposes only `Probe` and destructive `Stop`. It has its own bounded binary codec, nonces, per-Core incarnation identity, and dedicated listener path; it never constructs `CoreClient` or depends on the current application protocol. A UI may offer **Stop Sessions and Quit** only after this endpoint authenticates the exact Core incarnation. If recovery authentication also fails, the UI offers retry and manual diagnostics rather than killing by PID or spawning a competing Core.
- Attachment returns a complete `CoreSnapshot` containing the aggregate revision plus stable resource IDs and per-resource revisions.
- Reconnect is routine: attach, inspect or explicitly acquire the Control Lease, request a fresh snapshot, then subscribe from the snapshot's event sequence. A client must resnapshot after an unknown sequence gap or explicit stale response.
- Multiple UI Clients may attach concurrently. The first attachment acquires a vacant Control Lease; later attachments are observers that may read snapshots and terminal invalidations but cannot input or resize. The controller can explicitly transfer the lease to a connected observer. Controller disconnect advances and vacates the lease; an observer must explicitly acquire it rather than being promoted implicitly.

## Commands, events, and pressure

- Each connection serializes commands, and every command receives exactly one acknowledgement or structured error. Destructive commands are explicit and idempotent where retry is possible.
- Input and resize carry the caller's current lease generation. Authorization remains serialized until the terminal worker acknowledges the command, so transfer cannot overtake accepted input or resize. Observer, vacant-lease, stale-generation, and unavailable-transfer-target failures are structured responses rather than strings. Resize updates libghostty-vt and PTY/ConPTY through the ordered barrier before its acknowledgement.
- Semantic events are reliable and ordered by one monotonically increasing sequence. Natural Terminal Session exit emits the resulting hierarchy revision, failures retain a lifecycle event, and every Control Lease transition remains explicit; later resource and agent modules extend this same event class rather than sharing the coalescible visual path.
- Terminal visual updates are a separate pressure class. They carry only invalidation/revision information and may be coalesced; the client requests the latest terminal snapshot. Raw PTY bytes never cross the protocol.
- Terminal snapshots encode revision and Running/Exited/Failed lifecycle state. Natural exit is transitional: after final output is drained and the process is reaped, the Resident Core removes that Terminal Session and its Pane rather than publishing a lasting exited projection. A conditional snapshot request returns no payload when a running terminal revision is unchanged, so an idle UI neither rebuilds Ghostty snapshots nor rerenders. When it has changed, the Resident Core consumes libghostty-vt's dirty-row state and sends an ordered update based on the client's last revision. The UI Client replaces only the named rows in its local snapshot. Attach, resize, an unknown base revision, or a detected sequence gap forces a complete recovery snapshot.
- Protocol version 3 adds a server-pushed `TerminalChange` wake hint carrying an event sequence and terminal revision. Each client subscription uses a capacity-one nonblocking wake plus a latest-value map; protocol version 7 keys that map by Terminal Session ID so activity in one terminal cannot erase the only pending wake for another. The subsequent snapshot is authoritative, and neither a stalled socket writer nor a stalled UI consumer blocks the terminal worker. Disconnect removes the subscription immediately.
- Protocol version 4 gives every connection a stable `UiClientId` and the current `ControlLease` during attachment. Lease inspection, acquisition, and transfer use explicit protocol commands; every successful transition advances its generation. Observer attachment and terminal subscriptions share no process or terminal ownership with the UI Client.
- Protocol version 5 gives `CoreClient` one internal response reader that routes command responses separately from coalescible terminal invalidations. `CoreDriver` waits on UI commands and those invalidations, requests a snapshot only for a newer terminal revision, and publishes the latest frame through a bounded update stream that GPUI awaits directly. The former 16 ms UI snapshot timer is gone. `AGENT_TERMINAL_DRIVER_STATS=1` reports pushed changes, snapshot requests, and published snapshots when the driver closes. An explicit protocol-level Detach closes the response reader and releases the Control Lease on normal UI shutdown without affecting Terminal Session lifetime.
- Protocol version 6 adds a semantic-event sequence baseline to attachment and routes lifecycle and Control Lease events through a separate bounded reliable queue. `CoreClient` rejects a sequence gap instead of guessing through it, updates its cached Control Lease from accepted events, and requires reconnect plus an authoritative snapshot after a local or Resident Core queue overflow. `CoreDriver` consumes this stream alongside commands and terminal invalidations, using lifecycle events to request the newest snapshot without changing the GPUI-facing visual coalescing behavior.
- Protocol version 7 includes the authoritative `CoreSnapshot` and one Control Lease per Terminal Session in attachment. Hierarchy commands carry the caller's expected aggregate revision and return a complete acknowledged projection or a structured model rejection. Input, resize, terminal snapshots, visual invalidations, lifecycle events, and lease transitions all name a stable Terminal Session ID. Paths retain their native Unix bytes or Windows UTF-16 code units rather than passing through lossy Unicode conversion.
- Protocol version 8 adds lease-controlled paste commands. The Resident Core resolves bracketed-paste mode against libghostty-vt after an ordered PTY/ConPTY reader barrier, then writes the encoded bytes as one terminal input operation.
- Cold-layout restore intent was removed without incrementing protocol version 8. Terminal launch frames retain and ignore the former Restore Disposition byte so an upgraded Desktop Shell can attach to an already-running v8 Resident Core. A newly started Core always publishes a fresh default hierarchy.
- Protocol version 9 adds atomic `CloseTab { tab_id }` and `CloseSpace { space_id }` commands so a UI Client can request either resource-level action without expanding it into multiple Pane commands.
- A slow client never blocks PTY consumption. Coalescible terminal notifications may be replaced by a newer revision. If the bounded reliable queue fills, the Core removes only that subscription and sends an explicit resnapshot-required response after its already accepted events; a client-side reliable queue overflow detaches that connection immediately. Sustained-pressure integration coverage verifies that the controller, Terminal Session, and other clients continue while the slow observer reconnects and resnapshots.

## Failure behavior

- UI Client disconnect, crash, or normal quit releases its lease while the Resident Core and terminals continue.
- After final PTY/ConPTY output reaches libghostty-vt, the Resident Core reaps a normally exited child and closes its Pane through the authoritative model. It retains failed terminals for actionable error presentation.
- Resident Core failure ends live-process continuity. Restart creates a fresh default hierarchy.
- Every cold Resident Core seeds a fresh opaque resource-ID namespace. IDs remain stable across UI Client detach/reconnect to that Core, while queued Pane or Terminal Session targets from a lost Core cannot alias unrelated resources in its replacement.
- The stable recovery endpoint first requests graceful shutdown. After a bounded grace period it may terminate its own Core process without running Rust destructors; acknowledgement means the stop was accepted, and the caller confirms endpoint disappearance before starting a replacement.
- Platform terminal transports must contain their hosted process trees independently of Rust `Drop`: Windows uses kill-on-close Job Objects, while Unix uses a guardian/lifeline that terminates the Terminal Session process group when the Core disappears. Until those adapters exist, Core crash means continuity is lost but surviving processes may be unmanaged; the product must not claim that every descendant is dead.
- A stale endpoint is never overwritten merely from a PID file. On Unix, the core holds an exclusive per-endpoint startup lock for its lifetime; only that lock owner may reclaim a same-user socket after a live connection probe fails. Windows named-pipe lifetime is managed by the kernel.
- Stopping the Resident Core is a separate acknowledged destructive command; closing a window, Pane presentation, or Desktop Shell never aliases it.
